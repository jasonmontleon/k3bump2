# k3bump2

On SpacemiT K3 boards (X100 cores) a hart can lock up hard while compiling Rust: it stops in user
mode and no longer answers anything, and the rest of the machine follows. `k3bump2` replays, in a
loop, the last 37,709 instructions one such `rustc` ran before its hart stopped, on that process's
own data at its own addresses, so the lock-up can be looked for without a Rust build.

**Running this can hard-lock the machine. The only way out is a power-cycle.**

## Is this a standalone reproducer?

It locks up the board, and so far it has done so every time: three runs, three lock-ups.

| System | Runs | Time until the first hart stopped |
|---|---|---|
| Fedora 45, kernel 7.3.4 (8 harts online), seven copies on harts 0-6 | 2 | 341 s and 71 s |
| Bianbu, vendor kernel (16 harts online) | 1 | under 1 s |

Not yet shown: that the hart stops at the same instruction as in rustc; that the missing page-table
entry is what decides it in this program (the `mapped` control has not been run yet); whether a
single copy is enough.

It is standalone in the sense that matters for running it: one static binary, no libraries, no root,
no Fedora files on disk. It is not small or clean, though: the 15 MB binary carries a piece of the
dead rustc's memory and 14 MB of code bytes copied from Fedora's `librustc_driver`.

On the board only two files are needed, `k3bump2` (the built binary) and `runwide.sh`. Everything
else is source or build input.

## The files

| File | What it is |
|---|---|
| `snap.bin` | The 203 memory pages that the last 37,709 instructions of the dead rustc touched, taken from the first memory dump (dump-1). 142 are code (134 from `librustc_driver`, 8 from other libraries), 34 read-only data, 10 writable data, 17 pages the run writes to (stack and heap). |
| `snap.h` | The index for `snap.bin`: each page's original address and kind, the 32 register values at the start of the stretch, the start address, the exit address, and the step where rustc died (37,679 of 37,709). Generated by `repro/tools/postmortem/mksnap.py` (not in this repository). |
| `extra.bin` | The other 3,514 `librustc_driver` code pages that were mapped in the dead process but not executed in that stretch, with bytes from the library file. Its last page holds the bytes of the page at `+0x2a20000`, used only by the control and the measurement. |
| `extra.h` | The list of addresses for those 3,514 pages. |
| `mkextra.py` | Generates `extra.h` and `extra.bin` from the dump's page-table record and the library file. Only needed to regenerate them. |
| `k3bump2_asm.S` | Program entry and system-call wrapper. `enter_window` loads the recorded registers and jumps into the recorded code; `window_exit` gets back out. It also embeds the two `.bin` files into the binary and holds the program's own stack. |
| `k3bump2.c` | The program itself (see below). |
| `runwide.sh` | Starts one `k3bump2` per hart and watches them. |

What `k3bump2.c` does:

1. **Setup:** pins itself to one hart, then puts every page at the address it had in the dead rustc.
   The page at `+0x2a20000` is left without a page-table entry, unless you pass `mapped` for the
   control.
2. **Measurement:** in a child process, checks whether the CPU fetches the never-executed lines near
   that page. Those are the "check:" lines in the output.
3. **Loop:** each pass restores the 17 written pages, resets the fresh heap page, loads the registers
   and runs the 37,709 recorded instructions. That stretch starts at rustc's `mprotect()` call, goes
   through the point where rustc died, and continues 30 instructions past it.
4. **Logging:** once a second it writes the "passes" line to the terminal and to `k3bump2.log`.

The `Makefile` builds it with clang as a freestanding static program.

## Build

The program uses no C library and no headers, and the generated inputs (`snap.*`, `extra.*`) are in
the repository, so the build needs only make, clang with the RISC-V target, and lld:

    apt install make clang lld        # Bianbu, Debian, Ubuntu
    dnf install make clang lld        # Fedora

lld is a separate package from clang. Without it the build stops with
`clang: error: invalid linker name in argument '-fuse-ld=lld'`.

The build works the same on the board and as a cross build on any other machine:

    make

That runs one command:

    clang --target=riscv64-linux-gnu -march=rv64gc -mabi=lp64d -mno-relax -O1 -ffreestanding -fno-pic \
          -fno-stack-protector -Wall -Wextra -nostdlib -static -fuse-ld=lld -Wl,--no-relax \
          -Wl,-z,norelro -Wl,--build-id=none -o k3bump2 k3bump2.c k3bump2_asm.S

With clang 23.1.5 (Fedora 45) the result is byte for byte the binary that locked the board:

    $ sha256sum k3bump2
    795791b7235aeb688aa0d82a2b57fcae6e30bc21e3cad1e87db65f5a5fadeb37  k3bump2

Another compiler version may give a different file. The recorded code and data are the same either
way; only the small loop around them is compiled.

## Run

### One hart

    ./k3bump2                 measurement (a few seconds), then 60 s of passes on cpu 3
    ./k3bump2 -t 3600         run for that many seconds
    ./k3bump2 -c 5            use another cpu
    ./k3bump2 mapped          control: the page has a page-table entry
    ./k3bump2 nocheck         skip the measurement
    ./k3bump2 -n              skip the mprotect() and page fault at the start of each pass
    ./k3bump2 -q              no "passes" line each second

It needs no root. It writes `k3bump2.log` in the current directory, synchronously, so the log is
complete up to the last line even after a power-cycle. A run that ends normally prints
`finished, N passes in T s, no hang`. One hart alone ran 60 s (865,408 passes) without a lock-up;
that is far too short to mean anything.

### One copy per hart: `runwide.sh`

`runwide.sh` must sit next to the `k3bump2` binary. Run it from a scratch directory:

    mkdir ~/bumpwide && cd ~/bumpwide
    /path/to/runwide.sh 0-6 4            # harts 0-6, 4 hours
    /path/to/runwide.sh 0-6 4 mapped     # control: the page mapped in every copy

Leave at least one hart out of the list: the watcher moves itself there, so that it does not freeze
together with a hart that dies. The two Fedora lock-ups in the table above came from
`runwide.sh 0-6 4`. After the first hart stops, the other copies stop too, over the next seconds to
minutes: other processes get stuck in the kernel waiting for the dead hart and take the remaining
harts with them.

Each copy logs to `hart<N>/k3bump2.log`. Once a second the watcher looks at every copy, and when one
stops making progress it says which kind of stop it is:

- the hart takes no timer ticks at all: the hart is dead (the lock-up);
- the task is asleep inside a system call: the hart is alive and the task waits for something;
- the task uses CPU time but its log no longer grows: it spins in the kernel or in its own code.

It then copies the stopped copy's writable memory to `stopped-hart<N>/`, which shows where in the
pass it stopped. Everything the watcher finds goes to the terminal and to `watch.log`, together with
the kernel version and command line. Logs of earlier runs in the same directory are renamed, not
overwritten. Ctrl-C stops all copies.

Treat the watcher as best-effort. Once a hart is dead, disk writes and ssh sessions can stall and
any process may get stuck, the watcher included. In the one lock-up it has been through so far
(Fedora), nothing after its start-up lines reached `watch.log` and no memory was saved. The
`hart<N>/k3bump2.log` files, which the copies write themselves, did survive and show when each copy
stopped. The kernel console is the reliable record of which hart died.

### What a lock-up looks like

The "passes" lines stop, and the machine stops answering over the following seconds to minutes. It
does not recover; power-cycle it. What the kernel prints on its console depends on how the kernel
was built.

Fedora has the lock-up watchdogs. The "hard LOCKUP" line names the dead hart; the "soft lockup"
lines are other harts that got stuck afterwards:

    watchdog: CPU0: Watchdog detected hard LOCKUP on cpu 1
    watchdog: BUG: soft lockup - CPU#3 stuck for 22s! [sshd:909]
    watchdog: BUG: soft lockup - CPU#4 stuck for 22s! [journal-offline:4082]

Bianbu's kernel has no lock-up watchdogs. After 21 s its RCU stall detector reports instead, and
the `cpu=` number is the dead hart:

    rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:
    rcu: rcu_preempt kthread timer wakeup didn't happen for 5249 jiffies! g12501 f0x2 RCU_GP_WAIT_FQS(5) ->state=0x200
    rcu:     Possible timer handling issue on cpu=3 timer-softirq=17105

### Without a K3

The program also runs under qemu user-mode emulation, which is how the replay was checked
instruction for instruction (it does not lock up there):

    qemu-riscv64-static ./k3bump2 -t 3 nocheck
